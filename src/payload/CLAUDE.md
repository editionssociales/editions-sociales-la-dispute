# src/payload

## Purpose

Le back-office Payload monté dans l'app (schéma Postgres dédié `payload`) : collections + globals, rôles/accès, hooks de revalidation à l'édition, et une surface admin custom (home `/admin` v4 — KPI ventes/newsletter, graphique, commandes, « En cours » —, vues `/admin/stock` · `/admin/sante` · `/admin/ventes`, chips de filtre livres/rencontres) au-dessus du CRUD généré. Cœurs purs et endpoints custom vivent dans `lib/`.

## Ownership

- **Owns** : la config des collections/globals, les policies d'accès (`access.ts` : `admin`|`editor`), les composants admin custom (`Dashboard.tsx`, `StockPage.tsx`, `HealthPage.tsx`, `VentesPage.tsx`, chips livres/rencontres/commandes, cellules de liste (`admin/cells/`, `admin/orders/`), champ slug), les endpoints custom et leurs cœurs purs dans `lib/`.
- **Does NOT own** : le modèle de domaine ni les seams de lecture du front (`src/lib`), les pages (`src/app`), la présentation (`src/components`).

## Local Contracts

- Dépendance à sens unique : `src/payload` importe parfois `src/lib` (type-only compris) ; `src/lib` n'importe jamais `src/payload` — seule la Local API (`getPayload`) relie les deux côtés. Cœur pur testé + orchestration I/O dans `lib/`, jumeaux `*-core.ts` (`stock-import`, `virements-import`, `import-run-report`, `order-export`).
- Écriture automatisée (import, migration) pose `context.migration`/`context.disableRevalidate` ; une écriture humaine ne les pose jamais — distinction lue par les hooks (`setContentTouched`, revalidation). Sur les collections catalogue (livres, auteur·rice·s, libellés, médias), le hook qui expire le data-cache tagué (`revalidate-catalogue.ts`) passe TOUJOURS avant celui qui purge les chemins ISR (`revalidate.ts`) dans `afterChange`/`afterDelete`, pour repartir de Postgres au re-rendu ; webhook de paiement et import stock revalident en plus explicitement via `revalidateCatalogueNow`.
- Endpoints custom gardés par `access.ts` en tête de handler, avant tout I/O : `isAdmin` pour ce qui peut écraser un état sensible (import stock), `isAdminOrEditor` pour le reste (imports qui n'ajoutent jamais, exports, rapports). Les deux endpoints d'export acceptent aussi `ids` (sélection explicite depuis les checkboxes de la liste, `src/lib/order-export.ts:parseExportOrderIds`, borné à `MAX_EXPORT_SELECTION`), qui PRIME sur `from`/`to` quand présent. Tout le reste (ex. désactivation d'un code promo) passe par le REST généré de la collection, sous sa propre `access`.
- Surface dashboard (`derive.ts`/`data.ts`) : jamais de vert ni de zéro par défaut — signal non calculable = `na` (pill grise, jamais masquée), bloc sans rien à montrer = MASQUÉ ; home limitée à 4 entrées par panneau (+ lien « voir tout »), sans aucun signal de retard de commande. File « Commandes à traiter » = `paid`/`prepared` natifs (l'historique Woo, purement numérique, en est exclu), précommandes comptées à part. `readSalesWindow` (home, 60 j) et `readSalesHistory` (`/admin/ventes`, 13 mois) partagent les mêmes dérivations pures et la même étanchéité comptable dons/ventes. `/admin/sante` porte l'état de la chaîne e-mail via `brevoConfigured()` — le même prédicat que le front, jamais une relecture parallèle de l'environnement.
- `payload.config.ts` porte deux pièges documentés en commentaire à la source : résilience Neon (`onInit` → `attachPoolErrorHandler`, `connectionTimeoutMillis` — un pool `pg` sans listener `error` tue le process au réveil d'autosuspend) et ordre de la nav admin (déclaration `collections` puis `globals` : un groupe qui ne contient que des globals atterrit toujours en dernier, quel que soit son rang de déclaration).
- `Orders` : `create` fermé à toute voie sauf le webhook Stripe (Local API `overrideAccess: true`) ; tout champ verrouillé après création sauf `status` ; idempotence par le couple `(stripeSessionId, orderType)`. `Ebooks` : collection séparée de `media`, à lecture RESTREINTE (`isAdminOrEditor`) — jamais de fichier numérique payant dans `media`, public par construction ; le lien titre↔fichier est porté par `ebooks.livre` (unique), jamais par un champ de `Books`. Contrat exact des deux (marqueurs d'effet, contrainte de rejeu des migrations de seed) documenté dans `Orders.ts`/`Ebooks.ts`, vérifié par `Orders.test.ts`.
- `VirementsSouscription` : seule collection dont la raison d'être est une lecture du front (jauge `/souscription`) — hooks de purge dédiés sur écriture ET suppression. Import du classeur : rapprochement idempotent par `cleImport`, ne supprime jamais une ligne (détail dans `virements-import.ts`).
- `Books` : `buy.parislibrairies`/`buy.lalibrairie` s'autoremplissent depuis l'ISBN au `beforeChange` humain, fail-open (détail dans `buy-links-autofill.ts` ; rattrapage via `scripts/backfill-buy-links.ts`, dry-run par défaut). « À paraître » n'est pas un champ mais une conséquence de `dateParution`, dérivée via `upcomingBoundaryUtc` (`src/lib/sellability.ts`).

## Verification

- `pnpm generate:types` après tout changement de schéma (collections/globals/fields) : `payload-types.ts` est commité, et c'est lui qui rend les comparaisons de rôle d'`access.ts` vérifiables par le compilateur — tant qu'il n'est pas régénéré, un champ ajouté n'existe pas pour `tsc` (piège constaté sur les marqueurs d'`Orders`).
- Les contrats d'accès sont EXÉCUTABLES, plus seulement écrits ici : `access.test.ts` exerce `isAdmin`/`isAdminOrEditor` directement, et `collections/Orders.test.ts` verrouille par inspection de config (aucune I/O) le `create` fermé partout et le verrouillage en écriture après création de TOUS les champs sauf `status`. Casser l'un ou l'autre fait rougir la suite, plus seulement la prose.
- Migrations versionnées, jamais de `push` en prod (cf. CLAUDE.md racine). `payload migrate:create` est inutilisable sur ce repo (snapshots drizzle obsolètes) : migrations écrites À LA MAIN sur le modèle des précédentes — convention arrays sous collection versionnée : table `_<coll>_v_version_<field>` avec `id serial` + `_uuid varchar` (l'array principal garde `id varchar`), colonnes nullable quand la collection a des drafts. Seed de DONNÉES dans une collection versionnée : Local API dans la migration (`payload.create`, `draft: false`, `context.migration`, idempotent par slug — précédent : produits contreparties), jamais un INSERT SQL brut qui sauterait la mécanique de versions.
