# src/payload

## Purpose

Le back-office Payload monté dans l'app (schéma Postgres dédié `payload`) : collections + globals, rôles/accès, hooks de revalidation à l'édition, et une surface admin custom (home `/admin` v4 — KPI ventes/newsletter, graphique, commandes, « En cours » —, vues `/admin/stock` · `/admin/sante` · `/admin/ventes`, chips de filtre livres/rencontres) au-dessus du CRUD généré. Cœurs purs et endpoints custom vivent dans `lib/`.

## Ownership

- **Owns** : la config des collections/globals, les policies d'accès (`access.ts` : `admin`|`editor`), les composants admin custom (`Dashboard.tsx`, `StockPage.tsx`, `HealthPage.tsx`, `VentesPage.tsx`, chips livres/rencontres/commandes, cellules de liste (`admin/cells/`, `admin/orders/`), champ slug), les endpoints custom et leurs cœurs purs dans `lib/`.
- **Does NOT own** : le modèle de domaine ni les seams de lecture du front (`src/lib`), les pages (`src/app`), la présentation (`src/components`).

## Local Contracts

- Dépendance à sens unique : ce dossier importe parfois `src/lib` (`donation-tiers`, `promo-core`, `order-export`, `cart-quote` en type-only) ; `src/lib` n'importe jamais `src/payload` — seule la Local API (`getPayload`) relie les deux côtés. Découpage cœur pur (testé, sans I/O) + orchestration I/O dans `lib/` — jumeaux `*-core.ts` pour `stock-import`, `virements-import` et `import-run-report` ; le cœur pur d'`order-export-handler` vit dans `src/lib/order-export.ts`.
- Toute écriture automatisée (import stock routeur, migration) pose `context.migration` et/ou `context.disableRevalidate` ; une écriture humaine ne pose jamais ces flags — c'est ce qui distingue les deux au niveau des hooks (`setContentTouched`, hooks de revalidation). Revalidation à l'écriture (4 collections catalogue : livres, auteur·rice·s, libellés, médias) : paire `revalidate-catalogue.ts` (expire le data-cache tagué `catalogue`) puis `revalidate.ts` (purge ISR CIBLÉE en chemins littéraux — listes + fiche du livre sauvé, ou fiches résolues par relation inverse pour auteurs/libellés/médias ; purge large réservée aux suppressions et au repli d'erreur — audit coûts Vercel 2026-08-23) — le hook tag TOUJOURS avant le hook chemins dans `afterChange`/`afterDelete` (read-your-writes, constaté en prod Vercel) ; l'import stock et le décrément de stock du webhook (`order-handler.ts`) revalident chacun explicitement via `revalidateCatalogueNow` (tag, listes, chemins littéraux des fiches écrites/vendues — plus de motifs).
- Endpoints custom gardés par `access.ts` (`isAdmin`/`isAdminOrEditor`) en tête de handler, avant tout I/O : `import-stock`, `export/preparation`, `export/compta`, `import-runs/:id/rapport`, `virements-souscription/import` (`isAdminOrEditor` — un import de virements n'écrase rien, contrairement à l'import routeur resserré à `isAdmin`). Tout le reste (ex. désactivation d'un code promo depuis le dashboard) passe par le REST généré de la collection, sous sa propre `access`.
- Surface dashboard (`derive.ts`/`data.ts`) : jamais de vert ni de zéro par défaut — signal non calculable = `na` (pill grise « indisponible », jamais masquée), bloc sans rien à montrer = MASQUÉ ; home : 4 entrées max par panneau (+ lien « voir tout »), plus AUCUN signal de retard de commande (décision client 2026-08-21), file « Commandes à traiter » = `paid`/`prepared` natifs (`number` contenant `CMD` — l'historique Woo, purement numérique, en est exclu) hors précommandes (comptées à part). UNE lecture par vue : `readSalesWindow` (60 j) pour la home — KPI 30 j glissants, graphique, précommandes par titre, vélocité stock — et `readSalesHistory` (13 mois) pour `/admin/ventes` (accès admin OU editor ; KPI 30/90/365 j, quotidien 30 j, mensuel 13 mois où l'historique Woo rend la saisonnalité lisible, top titres ; lien « Détail des ventes → » sous le graphique de la home) — mêmes dérivations pures (`windowSalesStats`/`monthlySalesBuckets`/`topTitles`), même étanchéité comptable dons/ventes. `/admin/sante` § « Configuration & accès » porte l'état de la chaîne e-mail : `BREVO_API_KEY` absente = `alert` (aucun e-mail ne part) avec l'adresse du repli manuel nommée ; le booléen vient de `brevoConfigured()` (`src/lib/brevo.ts`), le prédicat qui aiguille déjà le front, jamais d'une relecture parallèle de l'environnement.
- `Orders` : `create` fermé partout — seul le webhook Stripe écrit, en Local API `overrideAccess: true` (court-circuite l'access control, champs compris) ; tout est verrouillé après création sauf `status` (`lockedAfterCreate`) ; `stockDecremented`/`confirmationSent` = marqueurs d'effet du rejeu webhook (`order-handler.ts`), `admin.readOnly`. Idempotence par le COUPLE `(stripeSessionId, orderType)` (scission précommande et don avec contrepartie, cf. racine ; `indexes` unique) — `findOrderBySessionId` prend les deux arguments, `findOrdersByPaymentIntent` (pluriel) sert `charge.refunded`. `orderType: "don"` (client 2026-08-21) = étanchéité comptable DURE : exclu de tout agrégat de CA/TVA (part TVA vide dans `formatComptaCsv`, exclu de `salesStats`/`readSalesWindow` et donc de la carte KPI ventes de `Dashboard.tsx`), mais préparé/expédié comme une commande normale (export préparation, panneau « Commandes à traiter »).
- `Ebooks` (client 2026-08-24) : collection d'upload des fichiers numériques vendus, `read` RESTREINT (`isAdminOrEditor`) — à l'opposé de `media` (public, URLs Blob directes) : un ePub payant déposé dans `media` serait publié. Le lien titre↔fichier est porté par `ebooks.livre` (unique) et JAMAIS par un champ de `Books` : les migrations qui seedent `books` par la Local API (`20260821_160000_produits_contreparties`) rejouent avec le schéma COURANT — toute colonne ajoutée à `books` casse leur rejeu sur base neuve, donc le build hermétique de la CI (constaté en écrivant ce chantier). Règle générale : avant d'ajouter une colonne à une collection seedée par Local API dans une migration, rejouer `pnpm migrate` sur une base VIERGE.
- `VirementsSouscription` (client 2026-08-24) : les contributions à la souscription encaissées HORS Stripe — seule collection dont la raison d'être est une lecture du FRONT (`src/lib/virements.ts` → jauge `/souscription`), d'où les hooks de purge (`revalidateSouscriptionNow`) sur écriture ET suppression. L'import du classeur (`lib/virements-import.ts`) rapproche par `cleImport` — crée / met à jour / laisse tel quel, ne supprime JAMAIS (les lignes en base absentes du fichier, dont les saisies manuelles sans `cleImport`, sont seulement listées dans le rapport) — et purge UNE fois en fin de run (`context.disableRevalidate` sur chaque écriture), même parti pris que l'import routeur.
- Résilience Neon : `onInit` branche `attachPoolErrorHandler` (`lib/pool-error-handler.ts`) — sans listener `error` sur le pool `pg`, un client idle coupé à l'autosuspend Neon (plan Free, ~5 min) tuait tout le process Vercel (constat prod 2026-08-07) ; même motif pour `connectionTimeoutMillis` borné dans `payload.config.ts`.
- Nav admin = ordre de déclaration dans `payload.config.ts` (tableau `collections` puis `globals`, un global rejoint le groupe existant à sa suite) ; groupes cibles : Quotidien (Livres, Commandes, Virements) · Catalogue (Auteur·rice·s, Libellés, Médias, Fichiers numériques) · Vie du site (Mises en avant, Rencontres, Page Souscription) · Boutique (Codes promo, Seuil stock) · Administration & technique (Utilisateur·rice·s, Imports routeur) · Pages du site (Pages des maisons, Page Contact, Mentions légales & pied de page). Piège framework (`groupNavItems.js`) : les globals sont traités APRÈS toutes les collections, donc un groupe qui ne contient QUE des globals (ici Pages du site) atterrit toujours en dernier dans le menu, quel que soit son rang de déclaration — assumé, cf. commentaire dans `payload.config.ts`.
- `Books` : `buy.parislibrairies`/`buy.lalibrairie` s'autoremplissent depuis l'ISBN au `beforeChange` humain (`autofillBuyLinks`, `lib/buy-links-autofill.ts`) — jamais sous `context.migration`, fail-open (une résolution en échec ne fait jamais échouer l'enregistrement, réessayée au prochain save) ; rattrapage de la base existante via `scripts/backfill-buy-links.ts` (dry-run par défaut, jamais lancé automatiquement). « À paraître » n'est PAS un champ (checkbox `aParaitre` supprimée, décision client 2026-08-21, migration `20260821_170000`) mais une conséquence de `dateParution` : dashboard (`readStockOutlook`/`readUpcomingBooks`) et chips de filtre le dérivent via `upcomingBoundaryUtc` (`src/lib/sellability.ts`) — fiche sans date comptée parue, comme `isUpcoming(null)`.

## Verification

- `pnpm generate:types` après tout changement de schéma (collections/globals/fields) : `payload-types.ts` est commité, et c'est lui qui rend les comparaisons de rôle d'`access.ts` vérifiables par le compilateur — tant qu'il n'est pas régénéré, un champ ajouté n'existe pas pour `tsc` (piège constaté sur les marqueurs d'`Orders`).
- Les contrats d'accès sont EXÉCUTABLES, plus seulement écrits ici : `access.test.ts` exerce `isAdmin`/`isAdminOrEditor` directement, et `collections/Orders.test.ts` verrouille par inspection de config (aucune I/O) le `create` fermé partout et le verrouillage en écriture après création de TOUS les champs sauf `status`. Casser l'un ou l'autre fait rougir la suite, plus seulement la prose.
- Migrations versionnées, jamais de `push` en prod (cf. CLAUDE.md racine). `payload migrate:create` est inutilisable sur ce repo (snapshots drizzle obsolètes) : migrations écrites À LA MAIN sur le modèle des précédentes — convention arrays sous collection versionnée : table `_<coll>_v_version_<field>` avec `id serial` + `_uuid varchar` (l'array principal garde `id varchar`), colonnes nullable quand la collection a des drafts. Seed de DONNÉES dans une collection versionnée : Local API dans la migration (`payload.create`, `draft: false`, `context.migration`, idempotent par slug — précédent : produits contreparties), jamais un INSERT SQL brut qui sauterait la mécanique de versions.
