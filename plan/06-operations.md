**Parti pris structurant (demandé par le mandat, aligné LEGACY-STACK §10.2 « H0 — tout de suite »)** : cette phase n'est **pas un bloc final**. Ce trou-là est fermé par **trois dispositifs complémentaires** : le contrat d'interface imposé à la phase Dons (capture Sentry explicite des erreurs *gérées* du handler), les notifications natives d'échec de livraison de Stripe (vérifiées : Stripe alerte par email un endpoint défaillant et le désactive après échecs prolongés), et un moniteur santé optionnel exposant l'âge du dernier événement Stripe reçu (cf. moniteur #8 et Dépendances).

### Jalon S1 — Erreurs + uptime + analytics (AVANCÉ à la phase Dons ; ~0,5 j, séquencé sur 2 jours — cf. Calage)

**Étape 1 — SDK Sentry dans l'app (branche, PR, previews vertes avant merge).**
- `pnpm add @sentry/nextjs` — **≥ 10.13.0** : c'est le seuil vérifié du support Turbopack (upload des source maps *après* le build, automatique) et le SDK v10 supporte Next `^16.0.0` ; le repo est en Next 16.2.9 où **Turbopack est le bundler par défaut**, donc pas de bascule webpack.
- Fichiers (conventions Next 16 lues dans les docs embarquées) :

  - `sentry.server.config.ts` (racine) : `Sentry.init({ dsn: process.env.NEXT_PUBLIC_SENTRY_DSN, environment: process.env.VERCEL_ENV, tracesSampleRate: 0, sendDefaultPii: false })`. Sobre : erreurs uniquement, pas de tracing, pas de PII (RGPD).
  - `src/instrumentation-client.ts` : même `Sentry.init` côté navigateur (+ `replaysSessionSampleRate: 0`, `replaysOnErrorSampleRate: 0`) ; `export const onRouterTransitionStart = Sentry.captureRouterTransitionStart` (breadcrumbs de navigation App Router).

### Jalon S2 — Sauvegardes Postgres + médias exportées (à boucler avant l'extinction douce des WP catalogue — la prod dépend de Neon dès le swap `CATALOGUE_SOURCE=pg`, qui rejoint désormais la fenêtre de bascule unique, 24–28/07 proposée, cf. `plan/02-mise-en-production.md` ; ~0,25–0,5 j)

**Étape 5 — Étage 1, natif fournisseur : restore window Neon.**
- À l'activation du plan Launch (phase catalogue) : configurer la **restore window à 7 jours** (PITR/instant restore — vérifié : Free = 6 h plafonné 1 Go ; Launch = jusqu'à 7 j, ~0,20 $/Go-mois sur un volume ici minuscule).
- **Vérification** : dashboard Neon → Backups/Restore affiche la fenêtre 7 j.

**Étape 6 — Étage 2, export externe quotidien : `.github/workflows/backup-db.yml`.**
- `schedule: cron "47 3 * * *"` (UTC, heure creuse — le cron GH n'est pas garanti à la minute, cf. Risque R5) + `workflow_dispatch` (déclenchement manuel pour la recette). Étapes du job (ubuntu-latest, ~2–3 min) :
  1. installer `postgresql-client` **à la version majeure du serveur Neon** (17 — dépôt apt.postgresql.org) + le binaire `age` ;
  2. `pg_dump --format=custom --no-owner "$NEON_DATABASE_URL"` (**URL unpooled/directe**, pas le pooler) → `catalogue-YYYYMMDD.dump` ;
  3. chiffrer **par clé publique** : `age -r age1… -o catalogue-YYYYMMDD.dump.age catalogue-YYYYMMDD.dump` — le destinataire `age1…` (clé publique de la paire P8) est **en clair dans le workflow, aucun secret de chiffrement en CI** ; la clé privée (fichier d'identité) ne transite jamais par GitHub. *(Le mode `--passphrase` d'age est interactif par conception et refuserait de tourner en CI — vérifié upstream ; l'alternative `age-plugin-batchpass` existe mais est inutile ici, la paire de clés est plus propre.)* ;
  4. upload sur le **store Blob PRIVÉ `es-ld-backups`** (script `@vercel/blob` ≥ 2.3 avec `BLOB_BACKUP_RW_TOKEN`, `access: 'private'`) sous `backups/daily/catalogue-YYYYMMDD.dump.age` ; le 1er du mois, copie supplémentaire sous `backups/monthly/`. Chemins datés déterministes **acceptables ici** parce que le store est privé (lecture authentifiée uniquement) — sur un store public ils seraient énumérables ;
  5. **copie additive des médias** *(s'active à la migration médias de la phase catalogue)* : `list` du store médias public → copie vers le store privé sous `media/<pathname>` des blobs **nouveaux ou modifiés** (comparaison pathname + etag/taille), **jamais de suppression côté sauvegarde** (une suppression accidentelle côté médias ne se propage pas) — ~15 lignes dans le même script. Couvre la promesse « sauvegardes » au sens du témoin devis (Duplicator sauvegardait fichiers + base, §3.5) après extinction des WP : toute couverture ajoutée via le back-office n'existera QUE dans Blob ;
  6. purge : `scripts/backup-prune.mjs` (`@vercel/blob` list/del sur le store privé) — garder 30 quotidiens + 12 mensuels (les copies `media/` ne sont pas purgées) ;
  7. **dernier step (succès uniquement)** : `curl "$BETTERSTACK_HEARTBEAT_URL"`.
- Heartbeat Better Stack : période 24 h, grace 6 h → alerte « sauvegarde manquante » si le job échoue, est droppé par GitHub, ou si le token expire. C'est ce qui rend la promesse du devis **vérifiable** au lieu de déclarative.
- Volumétrie/coût : base catalogue ≈ quelques Mo (293 livres ; les dumps SQL sources font 8–9 Mo) → ~0,3 Go de dumps à régime + ~0,2 Go de médias (originaux ~160–200 Mo, R3) ; coût Blob négligeable ; ~60–90 min Actions/mois (repo privé : quota 2 000 min).
- **Vérification** : run manuel (`workflow_dispatch`) vert ; blob présent et daté **sur le store privé** ; l'URL du dump répond 401/403 sans authentification (garde n°1 démontrée) ; heartbeat passé au vert ; `age -d -i backup-identity.txt catalogue-….dump.age | pg_restore --list` fonctionne (garde n°2).

**Étape 7 — Test de restauration (obligatoire avant d'éteindre quoi que ce soit).**
- Créer une **branche Neon** jetable → `age -d -i backup-identity.txt … | pg_restore --clean --no-owner -d <branch-url>` → requête de comptage (livres, auteurs, collections) identique à la prod → supprimer la branche. Documenter la procédure exacte dans `OPERATIONS.md` (y compris : où est le fichier d'identité, qui en détient une copie).
- **Vérification** : comptages identiques ; durée totale < 15 min (c'est aussi la répétition du plan de réversibilité devis §9 et du repli Scaleway de la décision stack).

**Étape 9bis — Surveillance du recouvrement boutique (drainage post-bascule ; engagement devis §5, ~0,1 j étalé sur ~2 semaines).** La boutique Woo/Paybox **cesse de vendre au jour J** de la bascule unique (`COMMERCE_NATIVE=1`) — ce n'est plus une passerelle de production vivante à mettre à jour mensuellement, mais une install **gelée** (gel de saisie posé à J−1, cf. `plan/02-mise-en-production.md`) qui ne sert plus qu'au drainage des commandes en cours, pendant le recouvrement (~2 semaines, J → J+14) :

- **Sécurité avant le gel** : dernière passe de mise à jour (cœur WP, WooCommerce, passerelle Paybox) **avant J−1** — après le gel, l'install ne prend plus d'écriture publique, la surface d'attaque se limite à `wp-admin` en accès équipe ; pas de cadence mensuelle à tenir au-delà, la garde s'arrête avec le recouvrement.
- Périmètre strict : disponibilité du drainage et des callbacks résiduels, pas d'évolution fonctionnelle de la boutique. Les WP **catalogue** ne sont pas couverts (ils cessent d'être la source dès le jour J) ; GEME jamais.

## Données et migration

Pas de migration de données dans cette phase. Deux flux de données créés :
- **Dumps + copie médias** : source = base Neon de prod (URL directe unpooled) + store Blob médias ; format `pg_dump -Fc` chiffré **age (paire de clés, clé publique seule en CI)** ; destination **store Vercel Blob privé** `fra1` (lecture authentifiée uniquement = garde n°1, contenu chiffré = garde n°2 — deux gardes réelles et indépendantes) ; vérification = étape 7 (restore sur branche Neon + comptages) ; **rollback de la chaîne elle-même** : supprimer le workflow ne touche à rien (la protection native Neon 7 j reste) ; rollback des données = la procédure de restore documentée. Perte du fichier d'identité age = dumps illisibles → deux copies (Youri + client) et l'étage Neon 7 j en filet.
- **Événements analytics/erreurs** : anonymisés (`sendDefaultPii: false`, WA sans cookie), rétention Sentry 30 j, région UE — rien à migrer, rien à archiver.

## Recette et critères d'acceptation (point de vue client)

1. **« Si le site tombe, quelqu'un le sait »** : simulation (keyword faussé ou maintenance simulée) → email d'alerte + push mobile en **< 10 minutes** ; rétablissement notifié.
2. **« Si un WordPress source — ou l'accès de drainage boutique — tombe, quelqu'un le sait »** : démontré une fois sur un moniteur source REST (#5/#6) et acté pour le proxy `/wc-api/*` (#7) et le `wp-admin` de drainage (#9).
3. **« Les erreurs remontent avec la ligne de code »** : une erreur de démonstration (server et client) visible dans Sentry avec fichier/ligne `src/…` lisibles + email reçu ; l'org Sentry affiche la résidence de données **UE**.
4. **« Des statistiques, sans bannière »** : le dashboard montre les visites du jour ; DevTools sur le site : **aucun cookie** ; aucune bannière de consentement nécessaire.
5. **« Une sauvegarde chaque nuit, que je peux récupérer »** : un fichier daté de la nuit précédente existe **sur le store privé** (inaccessible sans authentification — démontré) ; le client, avec le fichier d'identité age remis, télécharge, déchiffre et voit la liste des tables ; une restauration complète a été **démontrée** (étape 7) avec comptages identiques ; les médias ajoutés depuis la migration figurent sous `media/`.
6. **« Si la sauvegarde ne tourne plus, quelqu'un le sait »** : job désactivé un jour de test → alerte heartbeat « sauvegarde manquante ».
7. **« Si les webhooks Stripe décrochent pendant la campagne, quelqu'un le sait »** : démonstration à la recette dons — une signature invalide envoyée au handler produit un événement Sentry (contrat d'interface phase Dons) ; notifications d'échec Stripe vérifiées pointant vers des emails lus.
8. **`OPERATIONS.md` remis** et compris (survol 15 min avec l'équipe) ; propriété des comptes conforme au devis §9, voie de transfert Vercel actée (Q7) ; garde du recouvrement boutique (étape 9bis) déroulée jusqu'au drainage soldé.
